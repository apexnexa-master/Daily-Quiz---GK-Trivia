# Build a 2D Arrow Escape Silhouette Puzzle Game in Flutter

## 1. PROJECT OVERVIEW

Build a polished mobile puzzle game in Flutter inspired by the "Arrow Escape" style of puzzle games where the player taps long directional arrows to make them escape from a puzzle.

The most important visual and gameplay characteristic is:

> **The arrows themselves are arranged together to form recognizable silhouettes/pictures such as animals, birds, houses, vehicles, objects, symbols, etc.**

Do NOT interpret this as a grid of small square tiles containing arrows.

Do NOT create a voxel/3D block puzzle.

Do NOT create a collection of individual arrow icons placed inside square cells.

Instead, each puzzle consists of multiple **long, thick, connected-looking arrow-shaped paths**. The complete arrangement of those arrows forms a recognizable 2D silhouette when viewed as a whole.

# 6. ARROW PIECE DATA MODEL

An arrow should NOT simply be represented by a rectangle.

Each arrow should be a geometric path.

Example model:

```dart
class ArrowPiece {
  final String id;

  final List<Offset> points;

  final ArrowDirection direction;

  final double thickness;

  final double headLength;

  final double headWidth;

  bool removed;

  ArrowPiece({
    required this.id,
    required this.points,
    required this.direction,
    required this.thickness,
    required this.headLength,
    required this.headWidth,
    this.removed = false,
  });
}
```

The `points` represent the centerline of the arrow.

For example:

```text
P1
│
P2
│
P3 ───────── P4
```

The arrow is rendered around that centerline.

Arrowhead length:

approximately 1.8–2.4 × shaft thickness

# 24. COLLISION MODEL

Do NOT perform collision using only the arrowhead point.

The entire arrow path needs to be considered.

When an arrow is tapped:

1. Determine its direction.
2. Create an escape ray/path starting from the arrow's front.
3. Check whether another active arrow intersects the escape path.
4. If another arrow blocks it → cannot move.
5. If the path reaches the puzzle boundary without collision → arrow can escape.

Pseudo logic:

```text
canEscape(arrow):

    escapeDirection = arrow.direction

    escapePath =
        extend from arrow's arrowhead
        in escapeDirection
        until outside puzzle bounds

    for each other active arrow:

        if escapePath intersects other arrow:
            return false

    return true
```

---

# 25. IMPORTANT COLLISION DETAIL

Because arrows have thickness, use a collision shape rather than an infinitely thin line.

Represent each arrow as a stroked path or polygon.

For collision purposes:

```text
Arrow centerline
+
stroke radius
=
collision geometry
```

This prevents visually overlapping arrows from being considered separate.

# 26. TAP DETECTION

```text

+
tap tolerance
=

```

Use approximately:

```text

```

depending on screen size.

If arrows overlap visually, prioritize the top/frontmost or most recently rendered arrow.

# 34. GUARANTEE SOLVABILITY

This is mandatory.

Never ship a randomly generated level without checking that it can be solved.

For example:

```text
State:
remaining arrows

Find all arrows that can currently escape

For every available arrow:
    remove it
    create new state
    recursively solve

If all arrows removed:
    level is solvable
```

Use DFS/BFS with memoization.

# 54. RESPONSIVE RENDERING

All coordinates should be normalized.

Example:

```text

normalizedY = 0.0 → 1.0
```

Convert to screen coordinates:

```dart
screenX = puzzleLeft + normalizedX * puzzleWidth;
screenY = puzzleTop + normalizedY * puzzleHeight;
```

Never design levels exclusively for:

```text
1080 × 1920
```

# 55. TOUCH HANDLING

The player should be able to tap an arrow without precision.

Algorithm:

```text
onTap(position):

    candidates = findArrowsNear(position)

    sort candidates by render order

    for arrow in candidates:

        if hitTest(arrow, position):

            if canEscape(arrow):
                removeArrow(arrow)
            else:
                playBlockedAnimation(arrow)

            return
```

# 64. DEADLOCK DETECTION

The game should distinguish:

### Solvable state

At least one arrow can escape.

### Deadlocked state

There are active arrows but none can escape.

If the level generator produces:

```text
active arrows > 0
AND
available arrows = 0
```

reject the level.

During normal gameplay this should never happen if the puzzle was correctly generated.

---

# 65. GENERATING SOLVABLE LEVELS BACKWARDS

A strong level-generation technique is:

```text
Start with empty puzzle

        ↓

Add arrows in reverse solution order

        ↓

Create dependencies

        ↓

Reverse the solution

        ↓

Present puzzle to player
```

Example:

```text
Generation order:

A
B
C
D
E
```

Player's solution:

```text
E
D
C
B
A
```

This guarantees a known solution path.

Then add alternative branches to make the puzzle less predictable.

---

# 66. BRANCHING

Do not make every level:

```text
A → B → C → D → E
```

because that becomes boring.

Create branching:

```text
        B
       ↗
A ────
       ↘
        C

B → D
C → E
```

The player should sometimes have 2–4 valid choices.

The wrong choice should not necessarily make the level impossible.

This creates strategic decision-making.

---

# 67. AVOID FORCED SOLUTIONS EVERY TIME

Some levels can be:

```text
Only 1 valid move
```

for tutorial levels.

But later:

```text
3 possible moves
```

and the player needs to identify the best sequence.

This creates much better gameplay.

* difficulty comes from reasoning

# 74. COLLISION OPTIMIZATION

For small levels:

```text
O(n²)
```

may be acceptable.

For large levels:

Create spatial buckets:

```text
Screen
 ├── cell 1
 ├── cell 2
 ├── cell 3
 └── ...
```

Each arrow is registered in the cells it occupies.

When checking an escape path:

```text
query only nearby cells
```

instead of every arrow.
